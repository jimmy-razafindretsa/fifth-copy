# 0019. Production runs on Railway, replacing the single VPS

## Context
ADR 0012 chose one VPS with Docker Compose and Caddy, and left the provider open (Q4). On 2026-10-20 the owner chose Railway: the free Oracle Cloud ARM server could not be created (out of capacity in `ca-montreal-1`), and nobody on the team wants to run a server. Railway's first auto-import of the repo created one service per npm workspace (`@fifth-copy/protocol`, `@fifth-copy/engine`, `@fifth-copy/race-server`) with no database, no Redis and no variables, so every build or start failed on `src/env.ts` and `services/race-server/src/env.ts` validation.

## Decision
- **Project:** Railway project `perfect-endurance`, environment `production`, region `sfo`.
- **Services:**
  - `web` (still named `@fifth-copy/protocol` in the dashboard until renamed; private host `web.railway.internal`): repo root, Railpack builder, build `npm run build`, start `npm run start` on `PORT=8080`, pre-deploy `npx prisma migrate deploy` (migrations stay expand-only, ADR 0002), healthcheck `/api/health`. Watch paths: everything except `services/race-server/**`, `docs/**`, `work/**`, `agents/**`, `e2e/**`. A volume `avatars` is mounted at `/data/avatars` (`AVATAR_DIR`, ADR 0014).
  - `race-server` (`@fifth-copy/race-server`; private host `race-server.railway.internal`): build `npm run build --workspace=@fifth-copy/race-server`, start `npm run start --workspace=@fifth-copy/race-server`, port 4000, healthcheck `/health`. Watch paths: `services/race-server/**`, `packages/**`, `package-lock.json`.
  - `worker` (amendment #733, ADR 0011): repo root, Railpack builder, build `npm run build:worker` (esbuild bundle `dist/worker/main.mjs`), start `npm run start:worker`, one replica, no public domain and no port (it listens on nothing, so no healthcheck), draining time 120 s so a running job finishes on SIGTERM. Settings as code in `src/worker/railway.json` (config file path `/src/worker/railway.json`, also set in the dashboard, see the 2026-12-01 note below; asserted by `scripts/railway-config.test.ts`). Watch paths: `src/worker/**`, `src/features/**`, `src/server/**`, `src/env.ts`, `prisma/**`, `package.json`, `package-lock.json`, `scripts/build-worker.mjs`. It does not migrate: web's pre-deploy does, and a tick that meets a missing table logs and retries a minute later.
  - `Postgres` and `Redis`: Railway's official templates, each with its own volume.
  - `packages/engine` and `packages/protocol` are libraries bundled into the two apps; they are never services.
- **Domains:** each app has a Railway domain (`*.up.railway.app`). The browser opens Socket.IO directly on the race-server domain (`NEXT_PUBLIC_RACE_SERVER_URL`), allowed by `WEB_ORIGIN` CORS; no reverse proxy sits in front. A custom domain replaces both later without code changes.
- **Variables (names only):**
  - web: `DATABASE_URL` (reference to Postgres), `AUTH_SECRET`, `RACE_TOKEN_SECRET`, `RACE_SERVER_INTERNAL_URL` (`http://race-server.railway.internal:4000`), `NEXT_PUBLIC_APP_URL`, `NEXT_PUBLIC_RACE_SERVER_URL`, `AVATAR_DIR`, `REDIS_URL` (reference to Redis, with `?family=0`; required in production since #716: rate limiter and internal nonce store, ADR 0020), `NODE_ENV`, `PORT`.
  - race-server: `REDIS_URL` (reference to Redis, with `?family=0` so ioredis resolves Railway's private DNS over IPv4 or IPv6), `RACE_TOKEN_SECRET` (same value as web), `WEB_ORIGIN`, `RACE_SERVER_PORT`, `RACE_FAST_CLOCK=0`, `NODE_ENV`, `RACE_DRAIN_CAP_S` (optional, default 900, #704), and Railway's own `RAILWAY_DEPLOYMENT_DRAINING_SECONDS` / `RAILWAY_DEPLOYMENT_OVERLAP_SECONDS` (#704).
  - worker (#733): the web's `src/env.ts` validates at boot, so it takes the same names as references to the web's values: `DATABASE_URL` (reference to Postgres), `AUTH_SECRET`, `RACE_TOKEN_SECRET`, `REDIS_URL` (required in production by `src/env.ts`), `NODE_ENV=production`. No new variable name.
  - Secrets are generated with `openssl rand -hex 32` and piped into the Railway CLI (`railway variable set --stdin`); they are never printed, committed or pasted into issues. Rotation is a human task.
- **Backups (amendment #705, replaces the nightly `pg_dump` of card #407 / ADR 0012):**
  - **Mechanism:** Railway volume backups (docs: Data & storage > Backups), incremental and copy-on-write snapshots of a whole volume. Two volumes are covered: the `Postgres` service's data volume (the whole database) and the web's `avatars` volume (`/data/avatars`, ADR 0014). Redis is not backed up (no durable data, ADR 0008).
  - **Schedule and retention:** one **Daily** schedule on each volume (Backups tab of the service). Railway keeps a daily backup 6 days, so no copy outlives the 14-day window of `docs/privacy/retention.md`. The **Weekly** (27 days) and **Monthly** (89 days) schedules stay off, no backup is ever locked (a lock removes its expiry), and a manual backup (its expiry is not documented) is deleted as soon as the task that made it is over.
  - **Where copies live:** inside Railway, attached to the volume, in the same project and environment (`production`) and region (`sfo`, US West) as the data; encrypted at rest with AES-256 under Railway-held keys (docs: Enterprise > Security). Wiping a volume deletes its backups, so a volume is never wiped to "reset" it.
  - **Restore:** only in place, onto the same service in the same environment (Railway cannot restore a volume backup into another service or environment). Railway mounts a new volume built from the backup, stages the change, and keeps the previous volume unmounted as the rollback; the operator deploys, checks `npx prisma migrate status`, then deletes the unmounted volume once the restore is accepted. Exact steps and the restore drill: `docs/ops/backup-restore.md`.
  - **Not chosen:** Postgres point-in-time recovery (its archive keeps the last 4 weekly full backups, about 4 weeks, beyond the 14-day window, in a separate bucket whose credential is read-write) and a scheduled `pg_dump` service (an extra cron service, a bucket and credentials to run, for no restore gain at school scale).
- **Deploys:** Railway builds and deploys each service on push to `main` when its watch paths change. `NEXT_PUBLIC_*` values are build-time, so changing them needs a web rebuild.

## Consequences
- No server to patch, no Caddy, no Compose file, no SSH key in GitHub; Railway handles TLS and restarts.
- **Lost from ADR 0012:** race-server deploy-when-idle. Railway replaces the race-server container on every matching push. Railway's order (docs: deployments reference, deployment teardown): the new deployment boots, becomes Active once `/health` answers, takes the traffic, and only then the old one gets SIGTERM, then SIGKILL after the draining time (default 0 s, so live rooms were voided, ADR 0008).
- **Chosen strategy (#704): drain, not a manual deploy trigger.** On SIGTERM the race server marks `draining` on `/health`, refuses `POST /internal/rooms` with a 503 and `Retry-After` (the web's retry reaches the new deployment), keeps every live room ticking and exits when it serves no room, or at `RACE_DRAIN_CAP_S` (default 900 s: the longest timed race, 600 s, its countdown and results, with margin). Because the new deployment boots while the old one still runs on the same Redis, each process holds a lease (`instance:<id>`, 30 s TTL, refreshed); a race start stamps its room with the process id, and a boot voids a live race only once its owner's lease is gone (ADR 0008's restart rule, now scoped to rooms whose process is gone). Deploy settings, as code in `services/race-server/railway.json`: draining time 930 s (cap plus 30 s), overlap 0 s, health check `/health`; asserted by `scripts/railway-config.test.ts`. Railway reads that file only when the race-server service's config file path points to it (`/services/race-server/railway.json`), since it is not at the repo root. Config as Code files stop being read on 2026-12-01 (Railway docs), so the owner also sets the same values as the service variables `RAILWAY_DEPLOYMENT_DRAINING_SECONDS` and `RAILWAY_DEPLOYMENT_OVERLAP_SECONDS`; the race server logs a warning at boot when the first is below its cap.
- **Residual risk (#704):** the Railway docs state no maximum draining time and do not promise that open WebSockets to the old deployment survive until it exits (they "can still drop for other reasons, such as deploys"); the live test on production (#704 C4) checks both. A desk whose socket drops during the drain reconnects to the new deployment, which cannot resume it (no handover between instances): the race finishes for the others and stores their results. If the draining process dies before its race ends (cap reached, or killed), the new deployment voids that race within the lease TTL plus one reconcile period (about 90 s) and tells the sockets it holds. An untimed race longer than the cap is cut at the cap. Which instance `race-server.railway.internal` resolves to during the switch is not documented; a draining instance answers 503 and the lobby can be created again. Until #704 C4 is done, merges that touch `services/race-server/**` or `packages/**` land outside class time.
- CD smoke (`scripts/deploy-smoke.sh`) still needs a Railway equivalent. The nightly backup of card #407 is replaced by the Railway volume backups above (#705).
- **Backup limits (#705):** the newest restorable point is up to 24 hours old (daily schedule), so a restore loses the writes since that backup; a restore brings back accounts deleted after the backup, which the deletion purge (#81) must remove again; Postgres and avatars are separate snapshots taken at different times, so a restored avatar file may be missing or orphaned (the avatar store returns nothing for a missing file, ADR 0014). Backups live with the same provider and region as the data: they protect against a bad migration, a bad script or a lost volume, not against losing the Railway account.
- Cost: five always-on services (four before the worker, #733) plus volumes are usage-billed (roughly 5 to 15 USD a month at school load). This is not free hosting.
- Lock-in is small: both apps still build with plain `npm` and read only env vars, so moving to any Docker host later means writing the Dockerfiles ADR 0012 described.

## Alternatives considered
- **ADR 0012 as written (one VPS, Compose, Caddy):** full control and deploy-when-idle, but someone has to run and patch the server. The owner declined.
- **Oracle Cloud Always Free ARM VM:** free, but A1 capacity in the home region was unavailable, the free allowance was halved to 2 OCPU / 12 GB in 2026, idle instances can be reclaimed, and CI would need arm64 images. Rejected for now.
- **Vercel for web + Railway for race-server:** two providers and two secret stores for no gain over one Railway project. Rejected.
