# #101 Host-only race settings updates

- Date: 2026-10-07 (Builder). Branch `101-host-only-race-settings-updates-host-set`.
- Behaviour note (kept here, not in `packages/protocol/README.md`, so #101 stays off the `touches:protocol` lock #557 holds; the README already lists `host:settings`, its ack and the `settings` broadcast): the race server answers `host:settings` with `invalid` before touching Redis when the payload fails `hostSettingsSchema`; tolerates a missing ack callback; on a Redis error it logs `settings failed` and sends no ack (no wire code exists; the client resolves `timeout` after 5 s).
- Decisions: host = token `sub` === room hash `hostUserId` (ADR 0009, never the `role` claim); `registry.updateSettings` re-parses the patch with `raceSettingsPatchSchema` (in-process callers #156/#133), drops `undefined`-valued keys (#568 gotcha), merges top-level fields and `safeParse`s the whole object (`withDefaults` is never called: it throws); write = `HSET settings` + both EXPIREs in one MULTI (`withTtl`). Logs carry `lobby`, `outcome`, patched `keys`, never values.
- Client: `sendHostSettings` parses the ack with `clientAcks["host:settings"]`; an invalid ack goes to `onProtocolError` (`ProtocolError.event` widened to client-ack names) and resolves `timeout`; late acks are ignored.
- Known: socket.io-client buffers emits while disconnected, so a timed-out patch may still apply on reconnect (peers stay consistent via the broadcast). Floods of `host:settings` are #177's scope.
