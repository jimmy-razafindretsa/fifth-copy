# #543 CI never cancels main's run for a merge commit

- Date: 2026-10-07
- Outcome: `.github/workflows/ci.yml` concurrency is now one group per merge commit on `main` (`ci-<sha>`, cancel-in-progress false) and one group per ref with cancel-in-progress true elsewhere (PR refs unchanged). Deliver verdict: pass.

## Decisions
- Per-sha group on main, not just `cancel-in-progress: false`: a concurrency group keeps one running and one pending run, so a shared main group would still drop a queued merge commit's run (`mainCi: missing` at the Done gate).
- No deploy job runs in `ci.yml`, so overlapping main runs cannot race a deploy.
- The test evaluates the two expression shapes with a test-only mini evaluator (the yaml parser returns `${{ }}` verbatim); anything else throws.

## Gotchas
- The yaml-level test cannot prove GitHub's evaluation. Proof on GitHub: the PR run parsed and ran the new expressions; a second push to the PR cancelled the superseded run (PR-ref cancel kept). Main behaviour is observable only after merge: `gh run list --branch main --event push` should show no cancelled run for two close merges.
- `gh run list --commit` reports the latest attempt, so a cancelled-then-rerun main run reads `success`.
