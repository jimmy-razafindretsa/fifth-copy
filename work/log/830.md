# #830 Limiter #741 outage-warning test flakes under load

- Date: 2026-11-09 (builder).
- Reproduced: `src/server/limiter/index.test.ts` "#741" failed 1 of 15 runs under 6 CPU burners, then 1 of 27 with the latch instrumented. The failing run's sequence: timeout, timeout, timeout, **won the race** (latch reset), timeout: warned twice.
- Root cause (test, not code): the test built the slow limiter with `timeoutMs: 0` on the real, fast local Redis. Node clamps that timer to 1 ms, so a reply that reaches the poll phase before the timer is due wins `Promise.race`. A call that Redis answers in time ends the outage (`down = false`), so the next timed-out call starts a new outage and warns again. That is the intended production behaviour ("one warning per outage"); the test simply assumed every call would lose a race it can win.
- Fix: the test now puts a TCP proxy in front of the test Redis that holds every reply until `release()`, with a 20 ms timeout, so all five calls time out deterministically; releasing lets the late replies land and the count check still sees 5. `core.ts` unchanged: the latch already gives one warning per outage.
- C2: the file passed 30/30 under 8 CPU burners on 4 cores.
- Note: "fails open when Redis answers slower than the timeout" still uses `timeoutMs: 0`, but it makes one call on a fresh client (still connecting), so it cannot win the race.
- Follow-ups: none.
