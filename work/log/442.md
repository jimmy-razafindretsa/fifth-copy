# #442 School network compatibility: polling fallback race

Date: 2026-11-11. Outcome: when WebSocket is refused, the room socket falls back to Socket.IO long-polling. In e2e a full Clerk-bot race runs to the Dawn report over polling and stays within the 10 Hz budget.

## Decisions
- Transport choice (C1): keep ADR 0006's order (`["websocket", "polling"]`, one constant `ROOM_TRANSPORTS` in `socket.ts`) and add socket.io-client's `tryAllTransports: true`. Why not polling first with upgrade: ADR 0006 says "WebSocket first". With `tryAllTransports`, a refused upgrade goes on with polling in the same connect attempt, and an open network still ends on WebSocket. A unit test over a real Socket.IO server covers both cases. No ADR change.
- E2E WebSocket block (`blockWebSockets` in `e2e/race/helpers.ts`): an init script makes every `/socket.io/` WebSocket fail like a refused upgrade (`error`, then `close` 1006). Two alternatives did not work. `page.routeWebSocket` closing on open looks like a dropped line, not a refusal, and engine.io does not fall back on it. DevTools `Network.setBlockedURLs` lets WebSockets through. Next dev's HMR socket stays up, because blocking it reloads the page in a loop.

## Measured under polling (local `next dev` + race server, desktop project, E2E_TIMEOUT_SCALE=3)
- 182 snapshots. Snapshot interval: median 100 ms, p95 155 ms (budget 200 / 400).
- Keystroke to acknowledged cursor (the first snapshot whose `total` covers the key): median 129 ms, p95 241 ms over 56 keys (budget: median 300).

## Gotchas
- `recordRaceTokens` now also sees a `welcome` in polling responses, so `setHostSettings` works for a polling host.
- Residual risk: a proxy that holds the WebSocket upgrade open without answering makes the client wait for the connect timeout, and it does not fall back. The on-site test at the partner school is on the launch checklist (#438).
